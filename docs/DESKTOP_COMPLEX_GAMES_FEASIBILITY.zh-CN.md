# 桌面端"复杂游戏"可行性评估(World Creation · 方案 A 延伸)

> 背景:手机端(方案 A,WebView + LLM 生成单文件 HTML5)只能覆盖 2D 休闲/益智/棋牌/简单塔防等
> 轻量单机游戏。本文评估在**桌面端(Tauri 2.0 + WebView2 + Rust + 本地 LLM sidecar + Computer-Use)**
> 把可玩范围扩展到更复杂游戏的可行性、路径与成本。

## 0. 结论先行
- **桌面端能显著扩展可玩范围**,但"复杂"分三档,可行性递减:
  - **D1 富 2D / 轻 3D Web 游戏(强烈推荐,低成本)**:Three.js/WebGL、物理引擎(matter.js/
    Rapier-wasm)、较大代码量、本地存档、键鼠手柄 —— 桌面 WebView2 性能与内存远超手机,LLM 也能
    生成更大工程。**这是桌面端的甜区,ROI 最高。**
  - **D2 引擎导出型游戏(中等成本,推荐做"承载"而非"生成")**:用户/Agent 用 Godot/Phaser/
    PlayCanvas 等导出 Web 版(wasm+assets),平台**承载 + 分发 + 沙箱运行**,而非 LLM 一次性生成。
  - **D3 原生重型 3A / 实时大型多人(高成本,平台化而非生成)**:本质是"游戏分发/启动器 + 后端
    netcode",LLM 不参与生成游戏本体;桌面可作启动器,但偏离"AI 生成"主线,建议远期或合作模式。

## 1. 桌面 vs 手机的关键差异(为什么桌面能做更多)
| 维度 | 手机(RN WebView) | 桌面(Tauri WebView2/WKWebView) |
|---|---|---|
| 内存/CPU | 低端机吃紧,2vCPU 级 | 桌面级 CPU/GPU,GB 级内存 |
| GPU/WebGL | 受限、易掉帧 | 完整 WebGL/WebGL2,可跑 Three.js 场景 |
| 代码体积 | LLM 一次产出受限(~几百行稳) | 可多文件工程、分步生成、本地 LLM 大上下文 |
| 素材 | 难打包大素材 | 可落地到本地文件系统(Tauri fs)+ 本地 http 服务 |
| 原生能力 | 需逐个 RN 桥 | Rust 侧可开放受控能力(文件/进程/CDP) |
| 本地算力 | 无 | **localLLM sidecar 已存在**,可本地生成/迭代不烧云额度 |

## 2. 推荐路径 D1:桌面富 2D / 轻 3D Web 游戏(落地方案)
**复用现有桌面基建**:
- **承载**:Tauri WebView2 加载游戏(本地 `asset://` 或本地回环 http 服务托管多文件 bundle),
  比手机的单文件 srcdoc 宽松——可含 Three.js、wasm 物理、分离的 js/css/assets。
- **生成**:桌面端 `localLLM` sidecar(已实现)或云 LLM 生成**多文件工程**(index.html + game.js +
  assets manifest);桌面无手机的 token/体积焦虑,可"生成→本地试跑→自动修错"多轮(见 §4)。
- **沙箱**:Tauri CSP + 独立 WebView 窗口 + Rust 侧 capability 白名单(默认禁文件/进程/网络,
  仅放行游戏所需);用户生成代码**不得**触达 app token / 系统。这是做市场的硬前提。
- **存档/经济**:通过受控 `postMessage`/Tauri command 桥把"分数/通关"上报,**服务端校验**后
  挂 AXP(入场费/解锁/打赏;**不信任客户端分数**直接发钱)。

**可玩范围扩展到**:带场景的 2.5D/3D 小游戏、物理玩法(投掷/堆叠/赛车 lite)、更大的塔防/RPG
小关卡、多关卡平台跳跃、需较多代码的策略/模拟小游戏。

**成本估算(D1)**:后端复用 `creation_game_bundles`(html 字段改存"bundle 入口 + 多文件 blob"或
对象存储引用);桌面新增"游戏运行窗口 + capability 沙箱 + 桥"。约 1.5–2.5 人周(不含打磨)。

## 3. 路径 D2:引擎导出承载(中等)
- 用户/Agent 用 Godot(HTML5 导出)、Phaser、PlayCanvas、Construct 等产出 Web bundle 上传;
  平台**审核 + 沙箱运行 + 分发 + 交易**,LLM 仅辅助(生成脚本片段/资源描述),不生成引擎本体。
- 价值:质量上限高(真引擎);门槛:面向"会用引擎的创作者",非纯自然语言。
- 适合作为 D1 之上的"专业创作者通道"。

## 4. 共性硬问题(任何复杂度都要解决)
1. **生成可靠性**:复杂度↑ → 一次生成成功率↓。必须"**发布前自动试跑校验**":
   - 桌面用 **Computer-Use/CDP(已有)** 启 headless Chromium 加载 bundle,跑冒烟(无 JS 致命错、
     首帧渲染、基本交互无异常)→ 通过才可发布;失败把错误回喂 LLM 自动修(N 轮)。这是桌面相对
     手机的**独有优势**(手机端难做服务端试跑)。
2. **安全沙箱**:运行他人生成的代码 = 默认全禁(网络/文件/进程/eval 外联),逐项白名单。市场上线前提。
3. **经济防作弊**:分数→收益必须服务端权威/可验证;否则只用"入场费/打赏/解锁"等不依赖分数真伪的模型。
4. **跨端一致**:同一 Creation 在手机(轻量 HTML)与桌面(富 bundle)可给**两档产物**(mobileBundle /
   desktopBundle),发现/交易/社交层不变,仅运行宿主分端。

## 5. ❌ 仍不建议(即便桌面)
- 原生 3A(Unreal/Unity 原生包):分发/反作弊/体积/版权远超"AI 生成创作"范畴。
- 实时大型多人(MMO/吃鸡):核心是后端 netcode + 匹配 + 反作弊,与"生成"正交;如需,作为独立后端能力,
  不绑在创作生成里。
- 本地跑大型 ML/物理大模拟:即便桌面也需 GPU 专用,超出通用承载。

## 6. 建议的推进顺序
1. 先让手机端方案 A(轻量 HTML5)闭环稳定上线(进行中)。
2. D1 桌面富 2D/轻 3D:复用 localLLM + Computer-Use 试跑校验 + Tauri 沙箱窗口(主投入)。
3. 加"发布前 headless 试跑校验"(先桌面,反哺手机端发布门)。
4. D2 引擎导出承载作为专业创作者通道(按需)。
5. D3 平台化分发/netcode 远期或合作。

> 一句话:**手机管"随手造、随手玩"的轻游戏;桌面管"造得更像样、能玩更久"的富 2D/轻 3D。**
> 桌面的独门武器是 **localLLM(本地生成不烧额度)+ Computer-Use/CDP(发布前真机试跑校验)**,
> 正好补上方案 A 在手机端做不了的"复杂度"和"可靠性"两块短板。
