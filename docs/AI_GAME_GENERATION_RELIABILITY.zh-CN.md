# 首次生成游戏的可靠性:比"运行时+代码生成+自动修复"更有效的方式

> 问题:wow 的前提是"一次就能生成可玩的游戏"。除了 Astrocade 式"运行时 + agentic 代码生成 + 自动修复",有没有更有效的?
> 结论:有。最高杠杆的两件事是 **① 缩小任务(克隆变异,而非从零生成)** 和 **② 真执行验证(无头浏览器 play-test)再发布**。

## 核心认知:生成不可靠的真正原因
1. **任务太大**:让 LLM"从零写一个完整、好玩、适配手机的游戏"本质又难又不可控。
2. **没人验证产物是否真能跑**:多数失败是因为输出没经过"真的打开跑一遍"就上架(我们之前只做了静态校验,弱)。

→ 所以提升可靠性的两个最大杠杆就是针对这两点。

## 方法有效性排序(按"我们这种 移动端/有限算力"场景)
1. **参数化(配置)打在成熟引擎上** —— 可靠性最高,品类最窄。
   AI 只产出一份 JSON 配置(主题/难度/关卡/美术),引擎本身保证可玩+适配。**常见品类现在就该这么做。**
2. **克隆-变异(Clone-and-Mutate)+ 执行验证** —— 可靠性高、品类宽,**性价比最佳的扩品类方式**:
   - 从"已知能跑的游戏库"里**检索最接近的底座**(我们的自研/精选/历史好产物);
   - 让 AI 做**受约束的小改**(换主题/改规则/调参/换素材),**不是从零生成**;
   - **跑无头浏览器 play-test 验证**通过才发布。
3. **运行时 + 自由代码生成 + 自动修复 + play-test**(Astrocade 路线)—— 品类最宽,但需强模型+算力,可靠性中等。
4. **纯从零生成整段 HTML** —— 可靠性最差(我们最初的做法)。

## 比"运行时+codegen+repair"更有效的两板斧

### ① 克隆-变异,而非从零(把任务缩到 LLM 能稳定做对的尺度)
- 建一个 **known-good 游戏语料库**(自研精品 + 精选开源 + 通过验证的历史生成)。
- 生成时:检索最相近底座 → AI 只输出**差异**(主题/规则/参数/素材),底座本来就能跑。
- 这同时**让 remix 几乎免费**(remix = 底座换成"某个已有创作")。

### ② 真执行验证(自动 play-test + 修复),这才是真正的护城河
- 服务端用 **无头浏览器(Playwright/Puppeteer)** 真打开生成的 HTML:
  - 加载无 JS 报错;canvas/DOM 非空白;模拟点击/触摸后**状态有变化**(分数/位置);无外联越权。
  - 不过 → 把错误/截图回喂模型**修复**(有限次重试)→ 仍不过 → 回退到底座/模板。
- **谁都能调 LLM,少有人把"自动验证+修复"做扎实**——这是可靠性与体验的分水岭,也是别人难抄的工程壁垒。

## 给我们的落地建议(分阶段)
1. **现在**:常见品类走**参数化引擎 + AI 出配置**(消消乐/射击/俄罗斯方块已是现成引擎)——一次创作立刻可靠可玩。
2. **下一步**:加 **无头浏览器 play-test + 自动修复** 到生成管线(对"自由生成"和"克隆-变异"都适用)——这是可靠性的最大单点提升。
3. **扩品类**:用 **克隆-变异 + 语料检索** 放开品类,而不是堆死模板,也不是裸 codegen。
4. 强模型(BYO/高档)+ 自动修复回路兜底长尾。

> 一句话:最有效的不是"更强的生成",而是 **"把任务缩小(克隆变异)+ 真的跑一遍验证(无头 play-test)再发布"**。
> 这比纯"运行时+codegen+repair"更稳、更省算力,且让 remix 顺带成立。
