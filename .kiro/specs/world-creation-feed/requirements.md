# Requirements Document

> 世界创作与浏览(World Creation & Feed)— 需求文档

## Introduction

## 简介

本规格定义移动端「世界(World)」Tab 的一次重构,把当前**三套并行、概念重叠**的世界系统收敛为**一个统一的"活世界"**,并确立其核心循环:

> **创作(Create) → 发布(Publish) → 浏览(Browse,双模式) → 进入体验(Enter:玩 / 买 / 看 / 聊) → 互动(留言 / 点赞 / 分享 / 关注) → 反哺创作**

五大支柱:**创作、浏览创作、边玩边逛、交易、社交互动、分享**。

### 核心主轴:Creation 是"双接口单元"

系统的原子单位是 **Creation(创作)**,它是一个**双接口单元**:

- **对人**:可体验的应用/场所(玩游戏、逛店下单、看直播/脱口秀、漫游场所)。
- **对 Agent**:可被**检索、调用、代付交易**的服务/能力(类比 App Store + MCP 工具市场)。

两个接口是**同一份内容(ECS_World + offerings)的两个投影**,由 AI 自动派生,创作者只做"一个动作"(描述/搭建),**不手写任何接口**。由此产生**三个发现面**,共享同一个 Creation 注册表:

| 发现面 | 受众 | 形态 |
|---|---|---|
| 娱乐发现 | 人 | 创作流(类抖音,被喂、随机、社交) |
| 意图发现 | 人 | 世界地图 / 搜索(我想去/我想要) |
| 机器发现 | Agent | 能力检索 + 标准动词调用(代用户办事/交易) |

"Agent 也是消费者"为 **V1 主轴**,是本系统区别于 App Store(只有人意图发现)与抖音(只有人娱乐发现)的差异化引擎。

### 背景:当前三套系统

| 代号 | 名称 | 现状 | 本规格处置 |
|---|---|---|---|
| A | Aeon / 永曜城 | 真实地球地图圈地、建造目录、开公司雇 AI 员工发薪、任务悬赏、现场活动/直播舞台、地理签到、绑定真实商家 POI、现实任务奖励桥 | **保留**,作为"真实世界外壳 + 现实关联" |
| B | v6 世界创作平台 | 统一内容模型 ECS_World、分层基底 A/B/C、提示词/协同/手搭 创作连续谱、Agent 自治建造、可玩体验(超市下单、竞技场、塔防)、Plot 市场、审核、分享码 | **保留并升级**,作为"共创引擎 + 可玩体验" |
| C | v5 World Engine 战斗 | 扫描→角色→对战/副本/决策对战/UGC 战斗规则 | **删除**(不出彩) |

A、B 都含"圈地+建造",但后端是**两套独立表**(A 真实经纬度地块;B 抽象网格 `world_plots` + ECS)。本规格要求把它们合并为**单一的"创作(Creation)"对象模型**,并规划数据迁移/共存路径。

### 头号新能力:用户创作的"双模式浏览"

- **地图模式**:世界地图上的建筑即体验入口,点击直接进入用户创作的体验(基于地理位置探索)。
- **创作流模式(类抖音)**:竖向、可上下滑动的无限创作流。每条可以是一款游戏、一个超市(流内直接下单交易)、一场直播、一个脱口秀舞台,或任意 AI 生成的场所(学校/医院/咖啡馆/博物馆等,**不写死业态枚举**)。用户持续刷,刷到感兴趣的即可进入体验、留言、交易、分享。

### 范围说明

- 平台:移动端(React Native + Expo)为主;统一对象模型与后端契约需跨端可用。
- 回复/文档语言:中文。
- 安全:用户可运行内容必须遵守基底层级 A/B/C 的沙箱与能力白名单模型。
- 公开 UGC 进入创作流/地图前必须通过审核管线。

## Glossary

- **Creation(创作)**:统一的可发布/可发现/可进入/可分享对象。一个建筑、场所、游戏、店铺、直播、舞台都是一个 Creation。
- **Creation Type(创作类型)**:game / shop / livestream / stage / place(开放式)等;决定卡片渲染与流内行动。
- **Preview(预览物)**:供创作流滑动时轻量展示的封面图/短视频/回放/首帧截图。
- **Enter(进入)**:实例化并加载完整体验(较重)。
- **ECS_World**:B 的单一权威世界表示(实体-组件),人与 AI 写入同一结构。
- **Substrate Tier(基底层级)**:A=声明式场景;B=受限事件→动作 DSL;C=沙箱化逻辑模块(图灵完备,需更重审核)。
- **Economy_Bridge**:服务端权威的扣款/放款桥(AXP/USD);展示价仅为提示。
- **AXP**:世界内经验/货币,桥接全局钱包。
- **Agent_Builder**:可在用户离线时自治建造/维护创作的 Agent。

## Requirements

> 说明:本文件先建立骨架与首批需求,后续通过编辑逐条补全(每条含用户故事 + EARS 验收标准)。下方标注 `【待补全】` 的条目为占位,将在后续编辑中展开。

### 需求 1:统一的"创作(Creation)"对象模型

**用户故事:** 作为平台,我希望把 A、B 两套地块/建造模型统一为一个可发布、可发现、可进入、可分享、可计数的「创作」对象,以便地图与创作流共享同一份数据,用户的任何创作都能被一致地浏览与互动。

#### 验收标准

1. WHEN 一个创作被创建 THEN 系统 SHALL 以统一的 Creation 对象表示,且该对象具备唯一 id、创作者、类型(Creation Type)、生命周期状态、可选地理锚点(经纬度,可空)、可选地图网格坐标、预览物引用、内容引用(ECS_World 版本或等价体)。
2. WHEN 客户端请求浏览创作 THEN 系统 SHALL 通过统一的发现接口返回 Creation 列表,无论其底层来自原 A(真实地理)还是原 B(抽象网格)。
3. THE 系统 SHALL 为每个 Creation 维护互动计数(浏览数、点赞数、成交数、留言数)。
4. THE Creation SHALL 具备生命周期状态:`draft(草稿)` / `published(已发布)` / `listed(已上架交易)` / `under_review(审核中)` / `unpublished(已下架)` / `suspended(已封禁)`。
5. WHEN 一个 Creation 由 ECS_World 承载 THEN 系统 SHALL 通过版本引用(ecsVersionId 或等价)指向其当前内容版本,且内容编辑产生新版本而非覆盖。
6. THE Creation SHALL 支持可空的地理锚点(经纬度,用于地图模式)与可空的地图坐标;二者至少其一存在方可在对应浏览模式中出现。
7. IF 一个 Creation 既无地理锚点也无地图坐标 THEN 系统 SHALL 仍允许其仅出现在创作流模式(纯内容创作不要求选址)。
8. WHEN 统一发现接口返回 Creation THEN 系统 SHALL 同时返回其类型、预览物引用、创作者摘要、互动计数与"可进入(can-enter)"判定,供卡片渲染无需二次请求。
9. THE Creation SHALL 是一个"双接口单元":对人是可体验的应用/场所,对 Agent 是可被检索/调用/交易的服务。两个接口 SHALL 是同一份内容(ECS_World + offerings)的两个投影,而非两套独立产物。
10. THE Creation SHALL 包含 0..N 个 **Offering(供给项)**:每个 offering 描述一个产品/服务/能力,含名称、类型、价格(AXP/USD,可空)、可用标准动词集合,以及可空的地理/库存/可用时段。
11. WHEN 一个 Creation 发布 THEN 系统 SHALL 从其 ECS_World 与 offerings **自动派生**机器可读的能力清单(capability manifest),供 Agent 检索与调用,且 SHALL NOT 要求创作者手写任何接口/API。

### 需求 2:创作的创建与编辑(用户 / Agent / 共创)

**用户故事:** 作为用户,我希望用自然语言描述就能让 AI 帮我建出一个场所或游戏,也能继续协同编辑或手动微调,还能让我的 AI 在我离线时自治建造,以便低门槛地持续共创。

#### 验收标准

1. WHEN 用户提交一段自然语言提示 THEN 系统 SHALL 生成一个 Creation 的 ECS_World 草稿(提示词驱动 promptDrive)。
2. WHEN 用户在同一个 Creation 上切换创作方式 THEN 系统 SHALL 支持 `promptDrive(提示词)` / `coEdit(协同编辑,自然语言增改)` / `handBuild(手动搭建)` 三档连续谱,且作用于同一份 ECS_World。
3. WHEN 任一创作动作产生改动 THEN 系统 SHALL 以结构化 diff 记录新版本,并提供历史查看与回滚到任一历史版本的能力。
4. WHEN 改动由 Agent 产生 THEN 系统 SHALL 记录作者类型(user/agent)以区分归属。
5. WHERE 用户绑定了 Agent_Builder THE 系统 SHALL 允许该 Agent 在用户离线时自治建造/维护其 Creation。
6. IF 创作目标为 Tier_C(图灵完备逻辑模块)AND 发起端为移动端 THEN 系统 SHALL 强制把生成/编辑任务派发到桌面端或 Agent_Builder 执行,并向用户反馈任务状态。
7. WHILE 用户进行生成类操作 THE 系统 SHALL 校验月度成本上限与配额;达到软阈值时提醒、达到硬上限时阻断并给出明确文案。
8. THE 创作产物 SHALL 受声明的 Substrate Tier 约束:超出该层级允许的组件/能力时返回结构化的越界错误(TIER_VIOLATION)。
9. THE 创作 SHALL 保持"单一动作"低门槛:创作者只需描述/搭建创作本身,其 offerings 与对 Agent 的能力清单由系统自动派生,创作者无需手写接口或编写代码(Tier_C 自定义工具除外,见需求 13)。
10. WHEN 创作者标注一个商品/服务的价格或可用动词 THEN 系统 SHALL 同时将其用于人端展示与机器端 offering 清单(一次标注,两端复用)。
11. THE 系统 SHALL 支持以"描述→AI 生成"开放产出各类场所/业态(学校/医院/咖啡馆/博物馆等),不写死业态枚举;此为新业态的首选创作路径。
12. WHERE 创作输入为"扫描现实物体/资产" THE 系统 SHALL 把扫描结果作为创作素材纳入,但 SHALL 受**质量门槛**约束:输出须风格化、连贯、可作为资产/角色使用;未达门槛时不作为成品呈现(扫描能力的去留与放量取决于实际效果质量,见开放问题 1)。
13. 【待补全:多人共创(同一 Creation 多作者授权与并发)细则、模板/复刻、扫描质量门槛的客观判定标准】

### 需求 3:发布、审核与预览物

**用户故事:** 作为创作者,我希望发布我的创作并获得可分享的入口,同时系统保证公开内容经过审核,以便安全地进入地图与创作流。

#### 验收标准

1. WHEN 创作者发布一个 Creation THEN 系统 SHALL 先经过内容审核管线;仅通过后该 Creation 方可出现在地图/创作流并生成可分享短码与深链。
2. WHEN 一个 Creation 被发布 THEN 系统 SHALL 要求其具备至少一个预览物(封面图/短视频/回放/首帧),否则拒绝发布或自动生成占位预览。
3. IF 审核未通过 THEN 系统 SHALL 向创作者返回结构化的拒绝原因,且该 Creation 保持未发布状态(内容不丢失)。
4. WHEN 任意用户对已发布 Creation 提交举报 THEN 系统 SHALL 受理并在确认违规时将其状态置为 `suspended` 并移出地图/创作流。
5. THE 系统 SHALL 为每个 Creation 保留审核决策审计记录(谁/何时/结论/原因),供合规追溯。
6. WHEN 发布成功 THEN 系统 SHALL 返回可分享短码,并能解析为深链 + Web 预览兜底。

### 需求 4:双模式浏览之「地图模式」

**用户故事:** 作为用户,我希望在世界地图上看到各种建筑/场所,点击任一建筑就能直接进入对应的用户创作体验,以便基于地理位置探索世界。

#### 验收标准

1. WHEN 用户在世界地图上点击一个建筑/标记 THEN 系统 SHALL 进入该建筑所代表的 Creation 的体验(或其预览卡)。
2. THE 世界地图 SHALL 为单一地图,统一替代当前并存的 Aeon 真实地图与 v6 抽象网格地图。
3. THE 地图 SHALL 在标记上区分创作类型/商家(如店铺 POI 与居民创作的视觉区分),并展示创作者/名称。
4. WHEN 用户在地图空白处选址 THEN 系统 SHALL 允许圈地并在该位置创建/放置一个 Creation(把"建造"纳入统一创作)。
5. WHILE 用户开启定位 THE 地图 SHALL 支持显示附近的领地/创作与附近在线的人,并支持到访签到。
6. IF 地图原生组件不可用 THEN 系统 SHALL 优雅降级为列表/坐标选址模式,保证可用。
7. 【待补全:视口分页加载与在场刷新预算、地图与创作流之间的互通(从地图卡片切到流、从流定位到地图)】

### 需求 5:双模式浏览之「创作流模式(类抖音)」

**用户故事:** 作为用户,我希望像刷抖音一样上下滑动浏览大家的创作,刷到感兴趣的就停下来体验、留言、交易、分享,以便轻松地"边玩边逛"。

#### 验收标准

1. WHEN 用户进入创作流 THEN 系统 SHALL 以竖向可滑动的无限流呈现已发布 Creation,支持持续加载更多。
2. WHILE 用户在创作流中滑动 THE 系统 SHALL 仅展示轻量预览物(不实例化完整体验),并在用户显式进入时才加载完整体验。
3. THE 每条创作流卡片 SHALL 遵循统一的"带类型卡片协议":同一流内可混排 game/shop/livestream/stage/place,每类提供与其类型匹配的流内主行动(▶️玩 / 🛒买 / 🔴看 / 💬聊)。
4. THE 创作流卡片 SHALL 内联展示互动入口:点赞、留言、分享、关注创作者。
5. WHEN 用户在卡片上点赞/留言/分享/关注 THEN 系统 SHALL 即时反馈并更新对应计数。
6. THE 系统 SHALL 支持创作流的排序/推荐口径(如最新/热度/关注),并支持滑动方向上的预加载以保证流畅。
7. WHEN 用户停留在 shop 类卡片 THEN 系统 SHALL 允许直接在流内发起下单(走需求 7 的权威交易),无需先进入完整体验。
8. WHEN 用户停留在 livestream/stage 类卡片 AND 活动正在进行 THEN 系统 SHALL 允许直接进入直播/现场观看。
9. THE 系统 SHALL 为创作流提供冷启动内容供给:在内容稀少时以官方/种子创作与跨地域内容填充,保证新用户首次进入即有可刷内容,并明确推荐排序口径(最新/热度/关注/附近)。
10. 【待补全:举报入口、内容去重/防刷、空流占位、无障碍与省流模式、种子内容的运营来源】

### 需求 6:进入与体验各类创作

**用户故事:** 作为用户,我希望不同类型的创作都能在合适的方式下被体验——游戏能玩、超市能下单、直播/舞台能看,以便一个世界承载多样玩法。

#### 验收标准

1. WHEN 用户进入一个 `game` 类 Creation THEN 系统 SHALL 实例化其可玩体验并在 Substrate Tier 对应的沙箱隔离级下运行。
2. WHEN 用户进入一个 `shop` 类 Creation THEN 系统 SHALL 展示其商品(带价格组件的实体),并支持下单结账。
3. WHEN 用户进入一个 `livestream`/`stage` 类 Creation THEN 系统 SHALL 进入对应的实时直播/活动现场房间,支持观看与实时同框。
4. WHEN 用户进入一个 `place` 类(通用场所)Creation THEN 系统 SHALL 加载其场景供漫游与内部交互。
5. WHEN 进入体验耗时超过加载超时(如 10s)THEN 系统 SHALL 中止并回退到来源(地图/创作流),给出明确原因(LOAD_TIMEOUT)。
6. THE 体验内对宿主资源的访问 SHALL 限定在能力白名单内(deny-by-default),白名单外能力被拒绝并审计。
7. 【待补全:把已有 Aeon 房间/现场活动/公司空间映射为可进入体验、携带资产(只读)入场规则】

### 需求 7:交易(Economy_Bridge)

**用户故事:** 作为用户,我希望在体验内或创作流内直接对商品/服务下单付费,且金额由服务端权威计算,以便安全交易。

#### 验收标准

1. WHEN 用户在创作内发起购买 THEN 系统 SHALL 通过服务端权威的 Economy_Bridge 计算并扣款(AXP/USD),客户端展示价仅为提示。
2. IF 交易被拒绝或失败 THEN 系统 SHALL 保证用户余额不变,并返回结构化原因(如 ECONOMY_REJECTED)。
3. WHERE 交易涉及真实货币或高风险操作 THE 系统 SHALL 要求达到所需信任等级(如 Trust Level 3)并经签名确认。
4. WHEN 一笔创作交易完成 THEN 系统 SHALL 按一级/二级销售规则分配平台抽成,并将收益入账创作者。
5. THE 系统 SHALL 向创作者提供其 Creation 的销售/成交报表(按日)。
6. 【待补全:打赏/订阅等非商品交易形态、退款/纠纷处理边界】

### 需求 8:社交互动与分享

**用户故事:** 作为用户,我希望对创作留言、点赞、关注创作者并把创作分享出去,以便形成社区与裂变。

#### 验收标准

1. WHEN 用户对一个 Creation 留言 THEN 系统 SHALL 持久化该留言并展示在该 Creation 下,创作者可在收件箱看到。
2. WHEN 用户点赞/取消点赞一个 Creation THEN 系统 SHALL 即时更新点赞计数(幂等)。
3. WHEN 用户关注一个创作者 THEN 系统 SHALL 在该用户的"关注"创作流口径中纳入其后续作品。
4. WHEN 用户分享一个 Creation THEN 系统 SHALL 生成深链 + Web 预览兜底,未安装 App 的访客也能预览。
5. WHERE 体验为实时多人(房间/直播/广场) THE 系统 SHALL 支持实时同框、群聊与"打招呼/看主页"等社交动作。
6. 【待补全:私信入口、留言审核与举报、防骚扰/拉黑】

### 需求 9:现实世界关联

**用户故事:** 作为商家/用户,我希望把创作绑定到真实店铺/活动,并通过到访签到、完成现实任务获得世界奖励,以便虚拟世界与现实业务打通。

#### 验收标准

1. WHERE 用户为已认证商家 THE 系统 SHALL 允许把一个 Creation/地块绑定到真实店铺 POI(名称/类目/外部 POI id/店铺链接)。
2. WHEN 用户在真实位置到访某 Creation 的地理锚点附近(判定半径内)THEN 系统 SHALL 允许签到并发放 AXP 奖励,支持连续签到加成与打卡排行。
3. WHEN 用户在现实中完成关联任务 THEN 系统 SHALL 通过现实奖励桥幂等地发放世界 AXP,并记入收件箱/世界动态。
4. THE 绑定真实商家的 Creation SHALL 可链接到 marketplace 商品入口,支撑"逛到店铺直接下单"。
5. 【待补全:商家认证流程、反作弊(虚假签到)、隐私与定位授权边界】

### 需求 10:统一信息架构与世界 Tab 首屏

**用户故事:** 作为新/老用户,我希望进入世界 Tab 后清楚知道"现在能做什么、下一步去哪",而不是面对一堆分散入口,以便快速上手。

#### 验收标准

1. THE 世界 Tab 首屏 SHALL 围绕单一核心循环组织(创作 / 浏览 / 我的世界),收敛当前约 14 个并列入口与 3 个重叠的"世界"概念为一致的导航。
2. THE 首屏 SHALL 默认提供两个一级浏览入口:地图模式与创作流模式,且二者切换顺畅。
3. WHEN 新用户(无创作/无领地)进入 THEN 系统 SHALL 呈现单一主线引导(例如"圈一块地 / 描述一个场所让 AI 建出来"),不展示空的高级功能。
4. WHEN 老用户进入 THEN 系统 SHALL 优先呈现"回我的世界 + 我的创作 + 创作流",按用户状态渐进披露其余能力。
5. THE 首屏 SHALL 不再出现战斗/副本/决策对战/UGC 战斗规则/拍照→3D 等被退役的入口。

### 需求 11:退役战斗子系统与"照片直接当角色"

**用户故事:** 作为产品,我希望移除不出彩的战斗玩法与割裂的"原始照片直接当角色",以免拉低整体体验质感。

#### 验收标准

1. THE 系统 SHALL 从世界 Tab 移除对战、副本、决策对战、UGC 战斗规则相关入口与屏幕,并删除其后端模块、迁移与 E2E(战斗子系统整体退役)。
2. THE 退役 SHALL **保留扫描→资产生成管线**(scan→asset)作为创作输入——删战斗 ≠ 删整个 `world-engine`;扫描/资产生成基建予以保留。
3. THE 系统 SHALL 移除「拍照→3D 宠物」入口;并且不再将未风格化的原始扫描照片直接用作角色/资产形象。
4. WHERE 保留"扫描/描述→AI 角色或资产"能力 THE 输出形象 SHALL 经风格化生成或统一占位,且 SHALL 满足质量门槛(见需求 2 的扫描质量门槛与开放问题 1),不达标则不向用户呈现成品形象。
5. WHEN 用户通过旧深链/分享码访问已退役的战斗内容 THEN 系统 SHALL 优雅降级(提示已下线或重定向到相关创作),不报硬错误。

### 需求 12:A/B 合并与数据迁移

**用户故事:** 作为平台,我希望把 Aeon(真实地理)与 v6(ECS 创作)合并为统一创作对象,并规划平滑迁移,以便不丢失既有创作与经济数据。

#### 验收标准

1. THE 系统 SHALL 定义统一 Creation 对象与既有两套表(Aeon 真实地理地块、v6 `world_plots` + ECS)之间的映射关系。
2. THE 迁移 SHALL 保证既有创作、建造、地块、经济/货币数据不丢失,迁移后可被统一发现接口检索与进入。
3. THE 系统 SHALL 统一两套既有 marketplace 与经济入口(AXP/USD)为一致的交易/抽成模型。
4. THE 迁移 SHALL 支持灰度推进与可回滚(出问题可退回旧路径),并优先采用对用户不可见的平滑切换。
5. THE 合并 SHALL 采用**深合并**:以单一 Creation 注册表为唯一真相源,分阶段迁移——新建统一注册表 → 双写过渡 → 回填两套旧表 → 灰度切流 → 可回滚。
6. THE 统一 Creation 模型 SHALL 同时承载原 A 的地理锚点/真实关联与原 B 的 ECS 内容/分层基底,二者作为同一对象的不同维度,而非两套对象。

### 需求 13:Agent 对 Creation 的检索、调用与代付交易(机器发现面)

**用户故事:** 作为用户的 AI Agent,我希望能按需求检索全世界的创作及其提供的产品/服务,并代表用户调用、预约、下单,以便把"别人创作的能力"组合起来真正办成事。这是本系统区别于 App Store / 抖音的差异化引擎。

#### 验收标准

1. THE 系统 SHALL 提供面向 Agent 的检索接口,可按需求语义、能力/类目、价格、地理位置、信任级筛选并返回 Creation 及其 offerings 的能力清单。
2. THE 系统 SHALL 暴露一组**标准化、服务端中介的调用动词**作为 V1 的统一调用面:`query(查询信息/库存/价格)`、`order(下单购买)`、`book(预约服务/活动/座位)`、`message(留言或请求创作/其 Agent 办事)`、`subscribe(订阅)`、`donate(打赏)`;绝大多数创作 SHALL 无需自定义代码即可被这些动词调用。
3. THE 能力清单与上述标准动词 SHALL 以 **MCP 风格的工具** 暴露(每个 Creation 自动生成一组工具 schema),使平台内与外部 Agent 均可调用;平台 SHALL 在其上保留中介层负责鉴权、Economy_Bridge 权威结算、额度与审计(安全/经济正确性不外包给协议)。
4. WHEN Agent 代用户发起 `order`/`book`/`subscribe`/`donate` THEN 系统 SHALL 经 Economy_Bridge 服务端权威结算,且 SHALL 受该用户**预设额度(preset budget)**门控:在额度内免逐次确认、超出额度或授权范围时拒绝并要求用户重新授权,返回结构化原因。
5. THE 系统 SHALL 对每一次 Agent 调用执行鉴权、限流与审计(谁/代谁/调了哪个创作/动词/金额/结果),能力白名单外的调用一律拒绝。
6. WHERE 某 Creation 为 Tier_C 高级应用 THE 系统 SHALL 允许其 opt-in 声明额外的自定义可调用工具(经审核与沙箱),但这 SHALL NOT 成为创作者的默认/必需路径。
7. WHEN Agent 调用一个创作的能力 THEN 调用 SHALL 复用与人端一致的权威逻辑(同一份 ECS_World/offerings 与同一个 Economy_Bridge),不存在"机器走另一套规则"的旁路。
8. THE Agent 调用结果 SHALL 可回流为社交/世界信号(如成交计入互动计数、可生成世界动态),保持人机消费在同一世界内一致。
9. 【待补全:Agent 代付的授权撤销 UX、跨创作的多步编排(一个 Agent 串多个创作办事)、与既有外部 MCP/连接器(Aeon「派 agent 办真事」)的统一、费率与对创作者的结算口径】

## Open Questions

> 已决策(记录在此,作为后续设计前提):
> - **主轴**:Creation 为"双接口单元"(人可体验 + Agent 可检索/调用/交易)——已确认采纳。
> - **Agent 作为消费者**:纳入 **V1**(非二期)。
> - **低门槛原则**:创作保持"单一动作",Agent 能力清单由系统自动派生,创作者不手写接口。
> - **OQ1 扫描→AI 角色/资产**:**保留为目标能力,但质量门槛硬约束**;放量与是否最终保留取决于实际效果——达标(风格化、连贯、可用)才呈现成品,绝不直出原始照片。(写入需求 2.12 / 11.4)
> - **OQ3 新业态(学校/医院等)**:首选 **"描述→AI 生成"开放产出**,不写死枚举;同样以"做出好效果"为前提。(写入需求 2.11)
> - **OQ4 创作流冷启动**:**需要**做种子内容供给与推荐排序口径。(写入需求 5.9)
> - **OQ5 删除战斗深度**:**全删,含后端模块/迁移/E2E**;但**保留扫描→资产生成管线**作为创作输入(删战斗 ≠ 删整个 world-engine)。(写入需求 11.1–11.2)
> - **OQ6 Agent 动词集合**:在 `query/order/book/message` 基础上**增加 `subscribe(订阅)`、`donate(打赏)`**。(写入需求 13.2)
> - **OQ7 Agent 代付授权**:采用**预设额度(preset budget)**——额度内免逐次确认,超额/越权拒绝并重新授权。(写入需求 13.4)
> - **OQ8 暴露协议(建议采纳)**:能力清单以 **MCP 风格工具**暴露,平台保留中介层做鉴权/结算/审计。(写入需求 13.3)
> - **OQ2 A/B 合并深度**:采纳**深合并 + 分阶段迁移**(单一 Creation 注册表为真相源)。(写入需求 12.5–12.6)
